Run on the Hayato itself, like spec 001's report: the frame cost, the glyphs and
the window are hardware behaviour, and a chroot would answer for the machine that
built the image instead.

## What was exercised

`specs/002-design-system.md` - the token vocabulary, the widget set, the `App`
shell (header, body, key bar), the mouse, the density, the motion and the frame
budget.

## The window, at 152x45

`lazyos menu` in a 152x45 pty (`stty rows 45 cols 152`), with the release
binary of this branch, sending `q`:

```
LazyOS · the session menu                                        ────── … ──────
                                                          (a full-width rule)

                       ╭ LazyOS ──────────────────────────────────╮
                       │                                          │
                       │           the session menu               │
                       │                                          │
                       │        spec 007 - Esc closes              │
                       │                                          │
                       ╰──────────────────────────────────────────╯

 [Esc]  close   [q]  close
```

The three bands are there and the exit is the shell's: `exit=1` for `q` (Escape
would be the same), and the card is centred by `draw_empty` inside the body - not
by the command, which never sees a `Frame`.

## The measurements

| what | release | unoptimised |
|---|---|---|
| tick at 152x45, 40-row list, key bar | **424 µs** | 6.2 ms |
| allocations per frame | **0** | 0 |

`tests/budget.rs` renders 1 000 ticks after a warm-up and asserts the release
ceiling of 1 ms (10 ms while unoptimised, where the profile is not the device's).
`tests/no_alloc.rs` counts every allocation in the test binary with a global
allocator: 100 frames of a cached 40-row list allocate nothing, so the rule that
matters - the rows are built once per state, not per frame - is measured rather
than assumed. The two numbers are in `docs/optimization.md` §13, under *The shell
as shipped*.

## The glyphs

The widgets draw box-drawing and block characters. `lazyos --glyphs` prints them
from the binary and `check-system.sh` asks fontconfig for every codepoint in one
call:

```
$ lazyos --glyphs
U+2500 U+2502 U+256D U+256E U+256F U+2570
U+2588 U+258D U+2591 U+2595 U+2026 U+00B7

  OK    the framework's frame renders (12 glyphs, every codepoint covered by a font)
```

The check can fail: appending a codepoint no font has (`U+10FFFD`) to the same
list produced `missing:[ U+10FFFD]`, which is the FAIL branch.

## The shell rule

```
  OK    every command draws through the App shell (no Frame in lazyos-cli)
```

That is the same grep as `lazyos-cli/tests/frame.rs` (`ratatui::Frame`, `&mut
Frame`, `Frame<`), run on the device against the checkout, so a hand edit that
skips the test suite is still caught.

## The full framework section

```
==> The framework
  OK    lazyos is installed (.../target/release/lazyos)
  FAIL  lazyos reports 0.4.1 but the image was built from 0.4.0 (a stale /usr/bin/lazyos)
  OK    lazyos --help lists the menu
  OK    /usr/bin/lazyos-menu -> lazyos menu
  OK    sway floats and centres lazyos-pick
  OK    sway floats and centres lazyos-task
  OK    the framework's frame renders (12 glyphs, every codepoint covered by a font)
  OK    every command draws through the App shell (no Frame in lazyos-cli)
```

The FAIL is the check working: the card was built from `VERSION = 0.4.0` and
this branch's binary carries 0.4.1 (the repository's `VERSION`), so the next
build clears it. The report was taken with the branch's binary first on `PATH`;
the image's `/usr/bin/lazyos` predates `--glyphs`, which is why the glyph line
would otherwise have said "printed nothing".
