# Hardware validation reports

Raw output of `scripts/check-system.sh`, captured **on the machine itself**. They
are the evidence that this port is checked against the hardware and not only
against a chroot, where `/proc`, `/sys`, `dmesg` and `systemctl` describe the
host and every reading is meaningless.

Nothing here is generated by the build; each file is a copy of what the script
printed on the device.

A report has exactly one edit applied to it before it is committed: the
controller's MAC address is masked down to its OUI (`74:4C:A1:XX:XX:XX`). The
reports are published, and the hardware address of one particular machine is
evidence of nothing here — unlike `74:4C:A1`, which says whose radio it is.
Everything else, error lines included, is verbatim.

## check-system-2026-10-16-card.txt

First report from a booted image — the 2-partition card, from before the layout
in `scripts/lib-cgpt.sh` was written to it — run as the desktop user:
**41 OK, 3 WARN, 2 FAIL**.

Read it with the outcome in mind, because three of those five non-OK lines were
bugs in the *checks*, fixed afterwards (commit `b8e038a`, "check-system: fix
three false results from the first real boot report"):

| line in the report | what it really was |
|---|---|
| `WARN firmware the kernel asked for and did not get: mediatek/mt8192/scp.img` | Benign. `mtk-scp` is a module, so it asks for the firmware from the initramfs three seconds before the root filesystem exists; the journal shows `Booting fw image ... size 309164` and `SCP is ready. FW version asurada_scp_v2.0.20536` right after. The check now reports the outcome of the load, not the first attempt. |
| `WARN no swap active (zram-tools should provide /dev/zram0)` | The swap *was* active: `Adding 1948372k swap on /dev/zram0`, priority 100, in every recorded boot. greetd's session PATH has no `/usr/sbin`, which is where `swapon` lives. The check now extends its own PATH and reads `/proc/swaps` as a second source. |
| `FAIL the MT8192 sound card is absent: 49 alsa_card.platform-sound alsa` | The card was there and working. PipeWire names it after the platform device, not after the codec, so the codec-name grep missed it; `HiFi` and both sinks appear a few lines below. The check now fails only when no card exists at all. |
| `FAIL declared but not installed: zstd upower` | Expected: the card predates those two entries in `packages/base.list`. |
| `WARN 349 error-priority line(s) this boot` | The `sbs-8-000b` fuel-gauge noise, upstream (Nura's own log has it too) and documented in AGENTS.md. |

The rest is genuine hardware validation, and it is why AGENTS.md states what it
states:

* `OK depthcharge substituted kern_guid` and a `cmdline` that **does** carry
  `cros_secure` (depthcharge adds it), which is what makes disabling
  `depthcharge-tools`' system hooks a correctness fix and not only a build fix;
* `OK device tree: Google Hayato rev1`, `root=UUID=` present, modules installed;
* `OK panfrost loaded`, `OK backlight writable by group video (664 video)` and
  the session user in that group (the `brightnessctl` udev rule);
* `OK keyd.service is active`, `keyd leaves the sleep key alone` and
  `keyd matched its keyboard: ... (cros_ec)` — the Lock key fix;
* `OK controller powered` (bluez), `OK card active profile: HiFi` with the
  Headphones and Speaker sinks (the UCM boot sequence), `OK alsa 'default' PCM
  available (pipewire-alsa)`;
* `OK 5 suspend/resume cycle(s) recorded in this boot`, `OK clock synchronised`,
  `OK sway configuration is valid`, every sway command present, and all four font
  families found (the tofu-icon fix).

| line in the report | what it is |
|---|---|

`54213ae` — the only differences between the two commits are files that live in
the staged tree plus the one package — which is what the eMMC install will copy.

When a later report is taken, add it here next to this one instead of replacing
it: the diff between two reports is what shows a regression.

## foot-locale-warning.txt

One line, copied from the terminal that printed it:

```
warning: foot: 'C' is not a UTF-8 locale, falling back to 'C.UTF-8'
```

It is not a foot bug and not a missing locale: `/etc/locale.conf` carries
`LANG=en_US.UTF-8`, `locale -a` lists `en_US.utf8`, and `LANG=en_US.UTF-8 locale
charmap` prints `UTF-8`. What was missing is the variable reaching the session at
all.

**greetd does not pass its own environment to the session.** Its session worker
execs `/bin/sh -c "exec <cmd>"` with the **PAM environment alone**
(`pam_getenvlist()`), and Debian's `/etc/pam.d/greetd` brings in
`common-session`, which here contains only `pam_systemd` - no `pam_env`. So
`tuigreet --cmd sway` started sway with no `LANG`, every foot inherited that,
and the warning is foot falling back to `C.UTF-8`. Sorting, case-insensitive
matching and non-ASCII text were on the C locale for the same reason.

The fix is the one Debian's `/etc/pam.d/login` already uses:

```
session	required	pam_env.so readenv=1
session	required	pam_env.so readenv=1 envfile=/etc/default/locale
```

`rootfs-setup.sh` appends them to `/etc/pam.d/greetd` when it writes the greeter
configuration, and `pam_systemd` then passes the same environment on to the user
manager. The card this report came from was patched in place, so its next boot is
the one that proves it; an image built from the commit that carries the fix has
it without the patch.
