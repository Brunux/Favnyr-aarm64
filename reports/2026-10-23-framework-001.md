# 2026-10-23 - spec 001, the `lazyos` binary and its host

Run on the Hayato itself (eMMC install, swayfx session), not on the build host:
the dispatch, the window and the terminal restore are hardware behaviour, and a
chroot would answer for the machine that built the image instead.

## What was exercised

`specs/001-core.md` - the multi-call binary, the `argv[0]`/words dispatch, the
host's one-window rule, the terminal hygiene and the two states it can draw.

which is the drift the version check exists to report (see below).

## One window from the session, floating and centred

Started the way a binding starts it - no terminal, `WAYLAND_DISPLAY` set:

```
$ lazyos menu
$ swaymsg -t get_tree | jq '.. | objects | select(.app_id? == "lazyos-pick")
                             | {app_id, floating, rect, visible}'
{
  "app_id": "lazyos-pick",
  "floating": "user_on",
  "rect": { "x": 234, "y": 175, "width": 898, "height": 596 },
  "visible": false
}
```

898x596 is foot's client area for the requested 900x600 (two pixels of border),
centred on the 1366x912 panel: `(1366-898)/2 = 234`. The parent returned
immediately - the binding is never blocked by the window. `visible: false` is
the idle screen being up at the time of the capture, not the window.

Two mechanisms were tried before this one, and both are why the current one is
where it is:

1. **`swaymsg` from the app, before the first frame.** The app runs before
   foot's first commit, so the criteria matched no node: the window stayed
   `floating=auto_off` at `0,0 0x0`. Doing it after the first draw only moves
   the race, it does not remove it.
2. **`for_window ... resize set 900 600` in sway.** The rule applies at map
   time and foot then commits its own preferred size over it: a 900x600 rule
   produced a 700x496 window, while `move position center` still computed the
   position from 900 (x=233). The size therefore belongs to foot
   (`--window-size-pixels`), and placement to sway.

## The terminal after a forced panic

```
$ printf '' | script -qec "stty rows 45 cols 152; \
    LAZYOS_UI=1 LAZYOS_FORCE_PANIC=1 lazyos menu" /dev/null >/tmp/panic.out
exit=101
$ tail -c 120 /tmp/panic.out | od -c
... d i s p l a y   a   b a c k t r a c e \r \n
033 [ ? 1 0 0 6 l 033 [ ? 1 0 0 3 l 033 [ ? 1 0 0 2 l 033 [ ? 1 0 0 0 l
033 [ 0 m 033 [ ? 2 5 h 033 [ ? 1 0 4 9 l
```

The sequence is the module's own `term::RESTORE` (mouse tracking, SGR, cursor,
alternate screen), and it is the last thing written before the process exits -
the prompt that follows is the shell's, with the terminal it had. It appears
twice (the panic hook, then `Session`'s `Drop` during the unwind); the sequence
is idempotent.

## The witness on the device

```
$ scripts/check-system.sh          # ==> The framework
  OK    lazyos is installed (/usr/bin/lazyos)
  FAIL  lazyos reports 0.4.1 but the image was built from 0.4.0 (a stale /usr/bin/lazyos)
  OK    lazyos --help lists the menu
  OK    /usr/bin/lazyos-menu -> lazyos menu
  OK    sway floats and centres lazyos-pick
  OK    sway floats and centres lazyos-task
```

The FAIL is the check working: the card predates `VERSION = 0.4.1`, and the next
build clears it. Removing the installed link turns its line red as it should:

```
$ sudo rm /usr/bin/lazyos-menu
  FAIL  /usr/bin/lazyos-menu is missing or does not resolve to the lazyos binary
```
